# 架构决策记录 (ADR)

## ADR-001: 采用六边形架构 (Hexagonal Architecture)

**状态**: 提议中
**日期**: 2026-05-01
**决策者**: 架构团队

### 背景

OpenAkita 目前是一个单体应用，核心功能（Agent、记忆、工具、模型）紧密耦合。GenericAgent 项目则展示了更模块化的设计。为了融合两者优势，需要一个能够：
1. 保持核心稳定
2. 支持外部能力灵活扩展
3. 便于测试和替换实现

### 决策

采用六边形架构（端口与适配器）作为融合后的核心架构。

### 理由

1. **接口与实现分离**: 核心业务逻辑不依赖具体实现
2. **可测试性**: 端口可以被 mock，便于单元测试
3. **可替换性**: 可以替换适配器而不改变核心
4. **渐进式迁移**: 可以在不破坏现有代码的情况下逐步迁移

### 后果

**正面**:
- 代码更清晰，职责更明确
- 便于团队分工
- 支持插件化扩展

**负面**:
- 需要维护更多抽象接口
- 初期开发成本增加
- 需要处理适配器层的转换逻辑

## ADR-002: 使用 contextvars 隔离并发会话

**状态**: 已采纳
**日期**: 2026-05-01
**决策者**: 架构团队

### 背景

OpenAkita 需要支持并发会话，多个用户同时使用同一 Agent 实例时，需要防止状态串台。

### 决策

使用 Python 的 `contextvars` 模块实现 Task-Local Storage，隔离并发会话的上下文。

### 理由

1. **原生支持**: Python 3.7+ 内置，无需外部依赖
2. **自动传播**: contextvars 自动传播到子协程
3. **性能**: 比 threading.local 更轻量
4. **语义清晰**: 与 asyncio 任务模型天然匹配

### 实现

```python
_current_session: contextvars.ContextVar[Session | None] = contextvars.ContextVar(
    "_current_session",
    default=None,
)
```

### 后果

**正面**:
- 消除并发串台问题
- 代码更简洁
- 无需手动传递 session

**负面**:
- 需要注意子任务的上下文传播
- 在多线程环境需要额外处理

## ADR-003: 记忆系统多后端策略

**状态**: 提议中
**日期**: 2026-05-01
**决策者**: 架构团队

### 背景

记忆系统是 Agent 的核心能力，需要支持：
1. SQLite: 本地存储，简单可靠
2. ChromaDB: 向量检索，支持语义搜索
3. 可能的未来后端: Redis、Pinecone 等

### 决策

采用适配器模式，通过 MemoryPort 接口支持多后端。

### 理由

1. **向后兼容**: 现有 SQLite 实现可以作为默认适配器
2. **灵活性**: 用户可以根据需求选择后端
3. **可扩展**: 新增后端只需实现接口
4. **解耦**: 核心逻辑不依赖具体存储

### 接口设计

```python
class MemoryPort(ABC):
    async def store(memory: Memory) -> str: ...
    async def retrieve(query: MemoryQuery) -> list[MemoryResult]: ...
    async def consolidate(context: ConsolidationContext) -> ConsolidationResult: ...
```

### 后果

**正面**:
- 支持多种存储后端
- 便于性能优化
- 支持向量搜索

**负面**:
- 需要维护适配器层
- 不同后端可能有功能差异
- 数据迁移需要工具支持

## ADR-004: 工具系统 MCP 集成策略

**状态**: 提议中
**日期**: 2026-05-01
**决策者**: 架构团队

### 背景

OpenAkita 有成熟的工具系统，GenericAgent 可能依赖 MCP (Model Context Protocol)。需要统一两者的工具调用机制。

### 决策

1. 将 MCP 作为工具系统的适配器之一
2. 保持现有工具系统作为默认实现
3. 通过 ToolPort 接口统一访问

### 理由

1. **标准化**: MCP 是官方标准，有社区支持
2. **兼容性**: 可以使用 MCP 生态的工具
3. **渐进式**: 不强制迁移现有工具
4. **双向**: MCP 工具可以作为本地工具使用

### 后果

**正面**:
- 扩展工具生态
- 支持标准化协议
- 便于工具共享

**负面**:
- MCP 服务器需要单独部署
- 工具调用增加网络开销
- 需要处理 MCP 协议差异

## ADR-005: 特性开关实现方案

**状态**: 提议中
**日期**: 2026-05-01
**决策者**: 架构团队

### 背景

融合过程中需要保证稳定性，需要特性开关支持：
1. 灰度发布
2. 快速回滚
3. A/B 测试

### 决策

实现 FeatureFlags 类，支持：
1. 环境变量配置
2. 配置文件覆盖
3. 用户级别开关
4. 灰度百分比

### 理由

1. **简单**: 轻量级实现，无需外部服务
2. **灵活**: 支持多种配置来源
3. **可控**: 支持渐进式灰度
4. **可追溯**: 记录开关状态

### 实现

```python
class FeatureFlags:
    @classmethod
    def is_enabled(cls, flag_name: str, default: bool = False) -> bool:
        # 检查环境变量、配置文件、用户覆盖
```

### 后果

**正面**:
- 支持安全的发布实践
- 便于灰度验证
- 快速回滚能力

**负面**:
- 增加代码复杂度
- 需要维护开关列表
- 可能导致代码分支

## ADR-006: Ralph 循环保留为默认策略

**状态**: 已采纳
**日期**: 2026-05-01
**决策者**: 架构团队

### 背景

Ralph Wiggum 循环是 OpenAkita 的核心特性，保证任务永不放弃。

### 决策

保留 Ralph 循环作为默认执行策略，抽象为可插拔的 LoopPort。

### 理由

1. **差异化**: Ralph 循环是 OpenAkita 的独特价值
2. **成熟**: 经过充分验证
3. **可扩展**: 可以实现其他循环策略（ReAct、ToT 等）

### 后果

**正面**:
- 保持产品差异化
- 不破坏现有用户体验
- 支持策略扩展

**负面**:
- 需要维护多种循环策略
- 不同策略可能有不同适用场景

## ADR-007: OpenTelemetry 作为可观测性标准

**状态**: 提议中
**日期**: 2026-05-01
**决策者**: 架构团队

### 背景

需要统一的可观测性方案，支持追踪、指标、日志。

### 决策

采用 OpenTelemetry 作为可观测性标准。

### 理由

1. **标准化**: CNCF 项目，行业认可
2. **厂商中立**: 不绑定特定云服务商
3. **生态完整**: 支持追踪、指标、日志
4. **自动插装**: 支持主流框架

### 后果

**正面**:
- 统一可观测性
- 便于调试
- 支持多种后端

**负面**:
- 学习成本
- 配置复杂度
- 依赖外部服务

## ADR-008: Monorepo 作为代码组织方式

**状态**: 提议中
**日期**: 2026-05-01
**决策者**: 架构团队

### 背景

融合后需要管理多个模块，需要统一的代码组织。

### 决策

采用 Monorepo 结构，在 `/architecture` 目录下组织新架构代码。

### 理由

1. **统一**: 所有代码在一个仓库
2. **共享**: 便于模块间依赖
3. **CI/CD**: 统一构建和发布流程
4. **版本同步**: 便于依赖版本管理

### 结构

```
src/openakita/
├── architecture/          # 新架构代码
│   ├── kernel.py         # 核心内核
│   ├── ports/            # 端口定义
│   │   ├── memory.py
│   │   ├── tools.py
│   │   ├── model.py
│   │   └── collaboration.py
│   ├── adapters/         # 适配器实现
│   └── feature_flags.py  # 特性开关
├── core/                 # 现有代码（待迁移）
├── memory/               # 现有代码（待迁移）
└── ...
```

### 后果

**正面**:
- 代码集中管理
- 便于重构
- 统一工具链

**负面**:
- 仓库体积增长
- 需要工具支持（pdm-workspaces 等）
- 迁移成本
